# Session start and end

Bracket a checkout session on the terminal, so it knows when to start accumulating session-scoped state and when to discard it.

A checkout session is bracketed by two signals. **Start** announces that a checkout session has begun; the terminal may begin accumulating session-scoped state — evaluated offers, member identification, the displayed basket. **End** tells the terminal the session is over and that all session-scoped state it stored must be discarded.

Both signals are a standard nexo `AdminRequest` / `AdminResponse` exchange. The signal is carried in `AdminRequest.ServiceIdentification` as a versioned CSV (the nexo spec allows a name or CSV path):

- Start: `BiltSession,Start,v1,<sessionId>`
- End: `BiltSession,End,v1,<sessionId>`

`<sessionId>` is a UUID generated by the Sale System per session instance; it is the correlation key between the two signals. The format string is a versioned contract with the terminal firmware — any change to it requires bumping the `v1` version in lockstep with the terminal.

Send the brackets for every session — including refund-only sessions that reference a prior transaction and carry no basket.

---

## Before you begin

Make sure you have:

1. Ordered a terminal and boarded it to a store.
2. Read and understood the [Integration Guide](./integration.md).

## Start a session

Send the Start signal before any other request of the checkout — identification, display, loyalty, or payment. The session exists on the terminal only after the Start is acknowledged.

1. Send a Terminal API request with the following `MessageHeader` fields:

    - **`ProtocolVersion`** — `3.0`
    - **`MessageClass`** — `Service`
    - **`MessageCategory`** — `Admin`
    - **`MessageType`** — `Request`
    - **`ServiceID`** — Unique ID, 1–10 alphanumeric characters, unique within 48 hours per terminal.
    - **`SaleID`** — Your POS system identifier.
    - **`POIID`** — Target terminal ID, format: `[model]-[serial]`.

   And the following `AdminRequest` field:

    - **`ServiceIdentification`** — `BiltSession,Start,v1,<sessionId>`, where `<sessionId>` is a freshly generated UUID for this session instance.

   Example request:

   ```json
   {
     "SaleToPOIRequest": {
       "MessageHeader": {
         "ProtocolVersion": "3.0",
         "MessageClass": "Service",
         "MessageCategory": "Admin",
         "MessageType": "Request",
         "ServiceID": "SVC-01160",
         "SaleID": "BiltPOS-Lane3",
         "POIID": "VictaLane-275839164"
       },
       "AdminRequest": {
         "ServiceIdentification": "BiltSession,Start,v1,5f0e8a3c-2b74-4c1d-9e2a-6b8d4f7c1a90"
       }
     }
   }
   ```

2. The request is routed to the terminal. The terminal opens a session scope keyed by the session ID (and `SaleID`/`POIID`) and acknowledges.

3. On `Success`, proceed with the checkout. On `Failure`, no session exists — retry with a **new** session ID; never reuse the ID of a refused start.

---

## End a session

Send the End signal when the checkout is over — completed, voided, or abandoned. Do **not** end a session while money is in flight (a payment or void in progress) or while a failed payment's reversals are still outstanding: the terminal discards its session state on End, and reversals must complete before that state goes away.

1. Send a Terminal API request with the same `MessageHeader` fields as the start (a new `ServiceID`), and the following `AdminRequest` field:

    - **`ServiceIdentification`** — `BiltSession,End,v1,<sessionId>`, with the `<sessionId>` used at start.

   Example request:

   ```json
   {
     "SaleToPOIRequest": {
       "MessageHeader": {
         "ProtocolVersion": "3.0",
         "MessageClass": "Service",
         "MessageCategory": "Admin",
         "MessageType": "Request",
         "ServiceID": "SVC-01170",
         "SaleID": "BiltPOS-Lane3",
         "POIID": "VictaLane-275839164"
       },
       "AdminRequest": {
         "ServiceIdentification": "BiltSession,End,v1,5f0e8a3c-2b74-4c1d-9e2a-6b8d4f7c1a90"
       }
     }
   }
   ```

2. The request is routed to the terminal. The terminal discards all state accumulated for that session and acknowledges.

3. On `Success`, the session is over. Nothing may be sent for it afterwards — a new checkout requires a new Start with a new session ID. On `Failure`, the session is still open: the End may be retried.

## Session signal response

The result is returned in the API response in an `AdminResponse` body. A response without an `AdminResponse` body must be treated as a terminal error.

### Successful acknowledgement

- **`AdminResponse.Response.Result`** — `Success`.

  Example response:

  ```json
  {
    "SaleToPOIResponse": {
      "MessageHeader": {
        "ProtocolVersion": "3.0",
        "MessageClass": "Service",
        "MessageCategory": "Admin",
        "MessageType": "Response",
        "ServiceID": "SVC-01160",
        "SaleID": "BiltPOS-Lane3",
        "POIID": "VictaLane-275839164"
      },
      "AdminResponse": {
        "Response": {
          "Result": "Success"
        }
      }
    }
  }
  ```

### Failed signal

- **`AdminResponse.Response.Result`** — `Failure`.
- **`AdminResponse.Response.ErrorCondition`** — the reason for failure, with detail in `AdditionalResponse`.

  Example response:

  ```json
  {
    "SaleToPOIResponse": {
      "MessageHeader": {
        "ProtocolVersion": "3.0",
        "MessageClass": "Service",
        "MessageCategory": "Admin",
        "MessageType": "Response",
        "ServiceID": "SVC-01170",
        "SaleID": "BiltPOS-Lane3",
        "POIID": "VictaLane-275839164"
      },
      "AdminResponse": {
        "Response": {
          "Result": "Failure",
          "ErrorCondition": "NotFound",
          "AdditionalResponse": "Unknown session 5f0e8a3c-2b74-4c1d-9e2a-6b8d4f7c1a90."
        }
      }
    }
  }
  ```

For general guidance on handling failed requests, see [Handle responses](./error-scenarios.md).

---

## Terminal behavior

- A new Start for the same `SaleID`/`POIID` is treated as an **implicit End** of any previous session. A register that crashes never sends its End, so Start brackets are authoritative — the new session's Start clears whatever the crashed one left behind.
- End discards session-scoped state only. It never discards anything required to void or refund an already-settled transaction by its POI transaction reference — those flows carry the references themselves.
